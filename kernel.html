The agent does the work.
The host owns the workflow.

In 1.10 every task becomes a Mission with a written contract. The app, not the agent, decides what phase the work is in, what counts as proof, and when it is done.

Mission lifecycle

From a sentence to a verified result.

Six stages. Select one to stop the loop and read what happens there.

SQLite missions contract revisions route decisions agent runs evidence events

You say what you want. A Mission is created.

What happens
Your goal becomes a Mission attached to the chat, in the state "intake", with contract revision 1.
Who decides
You. The agent cannot create or close a Mission by saying so.
What is kept
The Mission, its first contract revision, and an event for each change — replayed after a restart.

The host routes the work to a playbook.

What happens
Fixed rules match the goal to one of 20 playbooks: bug fix, feature, investigation, refactoring and more. An unclear goal gets the safe one, Investigation.
Who decides
The rules, and then you: Change route stays available until the work starts. A route that costs more or reaches further asks you first.
What is kept
The decision, its reasons, and any override you made.

The route becomes a written contract.

What happens
The playbook's phases and the engineering principles that fit this task are written into a new contract revision. The agent is given only the instructions for the current phase.
Who decides
The host. A revision is never edited; a change is a new revision with a reason.
What is kept
Every revision, in order. Open the Contract button on the Mission bar to read it.

Agents do the work, inside the contract.

What happens
One agent, or a team shape you start yourself: Independent Verifier, Architect Panel, Arena, or Interrogate.
Who decides
The agent decides how. The host decides who may write: one writer per file, and reviewers are read-only and never see the author's reasoning.
What is kept
Each run with its participants and results — including the ones that failed or timed out.

The host runs the checks and records the result.

What happens
Each claim the Mission must prove is tied to a check from the project's Verification Profile — your tests, lint, build. The host runs it and stores the outcome.
Who decides
The result of the command. An agent can run commands but cannot record evidence, and "it passed" in chat is not a result.
What is kept
Every attempt, never rewritten. Edit the code after a pass and that evidence turns stale.

Done means every required claim has fresh evidence.

What happens
The Mission can only move to "completed" when nothing required is failed, stale, or missing. Otherwise the Evidence panel lists exactly what blocks it.
Who decides
The host, from the ledger. You can waive a claim, with a reason that stays on record.
What is kept
The final state, the waivers, and the trail that led there.

Who owns what

Three roles, kept apart.

An agent that grades its own work will pass it. So it doesn't get to.

You

Decide

  • The goal, and the route if you disagree with it
  • Which checks count, by activating a Verification Profile
  • Waivers, approvals, and every policy change
Host

Enforces

  • The Mission's state and every transition
  • Running checks and recording evidence
  • Whether the Mission may be called complete
Agent

Works

  • Reads, plans, writes, and runs commands
  • Follows the current phase's instructions
  • Cannot change the contract or certify its own result

Around the loop

Four more things the kernel makes possible.

Each one is a small loop of its own, run by the host.

Pause and resume

A pause, a usage limit, a backend switch, or closing the app all save what was true at that moment. Before anything continues, the host compares it with what is true now.

  1. Capture
  2. Compare
  3. Brief
  4. Resume

A changed branch or a missing worktree blocks Resume until you confirm it.

Impact

Finds what a change can affect outside its diff — importers, commands the frontend calls, code that reads a changed table — and turns it into checks to run.

  1. Change
  2. Dependents
  3. Unknowns
  4. Claims

What it cannot follow is listed as unknown, never left out. It edits nothing.

Pull request watch

Follows a pull request on GitHub or GitLab and tells you what still stands between it and merge-ready: checks, conflicts, review comments, approvals, and the Mission's own evidence on that commit.

  1. Observe
  2. Classify
  3. Act
  4. Verify
  5. Wait

It replies or re-runs a check only if you allowed it, once, after showing you. It never merges.

Workflow Lab

Run a routing candidate against a control on a fixed set of labelled cases, compare them segment by segment, and propose a policy change from the result.

  1. Run
  2. Compare
  3. Propose
  4. Approve

A proposal changes nothing until a person approves it. Too few cases is never a pass.

In your repository

Two files make a project its own.

Create them from Projects with one click, or let Onboarding add them.

.thanatos/verification.yaml

The checks a Mission must pass. A starter is built from the test, lint, and build commands the project already has. Nothing is in force until you activate that exact version.

.thanatos/playbooks/*.yaml

Adjust a built-in playbook for this project by adding steps or stricter gates. A file is used only after you approve it, and editing it afterwards needs approval again.
